02 · HOW IT WORKS

The model proposes; the application decides.

The CommonSwyft Harness is the channel-independent conversation service. The selected model is one replaceable component inside it.

1 · CHANNELWeb or WhatsApp

The channel transports messages; it does not own travel logic.

→
2 · MODELModel interprets

Produces one structured action. It does not call the backend directly.

→
3 · COMMONSWYFT HARNESSValidate + execute

Maintains trip state, enforces scope and calls an allowed tool.

→
4 · SOURCEFlights or policy

CommonSwyft API for live inventory; saved policy text for general questions.

→
5 · RENDERERUseful reply

Application code formats flight cards; sourced policy replies use the model.

Where it runs now

The demo harness runs on Google Cloud Run, the selected model is called through OpenRouter, and flight search runs against CommonSwyft staging.

What remains separate

The model and flight API remain external services. This personal experiment is not deployed inside CommonSwyft's production stack.

Memory ownership

The application stores memory, never the model. Today it is kept per browser and switched off here. With sign-in it would belong to the CommonSwyft account.

03 · MODEL CHOICE

Sonnet 5 is the default. Terra, DeepSeek and GLM remain controls.

Correctness on held-out cases was the gate. Values the model made up in its tool calls decided it. Speed and cost came after.

05 · SCOPE

Working, switched off, and deliberately deferred

This is a search assistant prototype, not a booking product.

✓ Working now

  • One-way, one-traveler flight search
  • City groups and explicit airports
  • Flexible/default dates and cabin
  • Follow-up changes within a conversation
  • Actual public staging search
  • Deterministic flight-card formatting
  • General privacy-policy retrieval with sources
  • “Take me anywhere” deals from the product's public feed
  • A link from every result to checkout on CommonSwyft
  • Weekly check that the policy snapshot matches the live pages
  • Support handoff and off-topic boundaries
  • Invite-protected Cloud Run web chat
  • Secret Manager for hosted credentials
  • Usage and infrastructure limits for the experiment

◐ Built, switched off

  • Conversation storage in Postgres, redacted, 90-day expiry
  • A stated home airport and the last origin as disclosed defaults
  • Recent searches listed by number at the start
  • Forget where I fly from, and forget my recent searches

Tested against a development database. It stays off here until the privacy page describes what is stored and for how long.

○ Backlog

  • Account sign-in and linking for WhatsApp or other channels
  • Production monitoring, alerts and operational ownership
  • MCP tools for compatible external assistants
  • Round trip, multi-city and multiple travelers
  • Richer destination discovery
  • Checkout for a specific quote, booking and payments
  • Ticket-specific refunds and booking lookup
  • Human approval and idempotency for consequential actions
  • Broader safety, privacy and adversarial evaluation
  • Temporary WhatsApp number using the same harness
06 · WHAT NEXT

The best learning path from here

Finish one credible product loop before adding more architecture.

  1. Switch memory on.Add the privacy-page sentence on storage and retention, then deploy with conversation storage on and watch for errors.
  2. Put recent searches in the model's context.So "the Tokyo one again" works, with new held-out cases that stop an old trip leaking into a new one.
  3. Checkout for a specific quote.Needs the traveler signed in to CommonSwyft and an approved API contract for quotes, expiry and revalidation.
  4. Check the judge against people.Compare its verdicts with human labels, since it shares a model family with the default.

How the deployed experiment works

1 · PHONEOpen an HTTPS chat

Open the invite-protected Cloud Run URL from a phone or laptop.

→
2 · HARNESSCloud Run executes

The personal experiment runs one bounded container.

→
3 · ACCESSExperiment login

A secure session cookie protects the demo. Account sign-in is backlog.

→
4 · SERVICESCall model + flights

The harness calls an API-hosted model and the existing CommonSwyft API.

The current deployment uses Cloud Run, Secret Manager and OpenRouter. It intentionally does not connect to production account data, booking or payments. Flight searches use the public staging API.
